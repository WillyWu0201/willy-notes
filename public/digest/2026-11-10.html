Locating the source of a mysterious beep with Claude

Simon Willison 讓 Claude Code 做出一套用多台裝置收音、定位神祕嗶聲的系統，關鍵是讓 agent 能透過麥克風「聽」到現場，並能即時推送新程式到各裝置自己做實驗。

重點

  • 先讓 agent 把問題寫成 problem.md，過程中它找到並讀了一篇 2007 年的聲學測距論文，研究方向確認後才開始實作。
  • 系統由 Python 伺服器協調，各裝置用瀏覽器 WebAudio 收音、以 WebSocket 回傳，偵測到嗶聲後播一段短音讓各裝置錄音片段能對齊。
  • agent 在聽眾端做了熱抽換模組的機制，可遠端送新程式執行，不必逐台重新整理頁面、重新授權麥克風，作者因此能放手讓 agent 持續迭代。
  • 自動定位裝置效果不佳，就加上手動拖曳的粗略模式；用拍手測試、加時間戳與重播功能，逐步建立對結果的信心。
  • 最後定位誤差約 40 公分，找到一顆電池快沒電的一氧化碳偵測器。作者認為最有意思的是替 coding agent 找到感知真實世界的方法。

反思問題

  • 你的 agent 能不能直接觀察程式在真實環境的執行結果，還是只能靠你轉述？
  • 在動手實作前，你會先讓 agent 把問題與可行性研究寫下來嗎？
  • 你有沒有辦法讓 agent 自己部署、觀察、再修改，而不需要你每一步都介入？

延伸閱讀

  • Beep Locator：本文專案的原始碼。
  • problem.md：agent 在動手前寫下的問題描述與研究整理。
  • BeepBeep 論文：2007 年用一般裝置的喇叭與麥克風做高精度聲學測距的研究，是本專案的方法基礎。
  • detector.js：用 FFT 與高通濾波偵測嗶聲的程式。
  • Martin Woodward 的除錯做法：用網路攝影機對著徽章螢幕，讓 coding agent 判斷更新是否成功。

Hide your slop PR descriptions behind

agent 寫的 PR 描述正確又完整，但長得讓人不想讀。Simon Willison 的做法是開頭放一段經過人判斷的簡短說明，完整的 agent 文字收進可展開的 details/summary 區塊。

重點

  • 問題不在 agent 寫得不好，而是寫得太詳盡，讀者一眼認出是 AI 文字就直接略過，不管內容多有用。
  • PR 開頭只放最短、能讓人快速理解用途的一段話，有時再加一張截圖，這段代表人的取捨判斷。
  • agent 的完整說明放在 GitHub Markdown 支援的 details/summary 裡，summary 寫模型名稱和推理強度，讓讀者清楚知道那是什麼。
  • 開頭不一定要自己寫，常常是從 agent 一大段文字裡挑出真正重要的那句；承諾的是這段值得讀者花時間。
  • 記標籤順序的小訣竅：summary 是點擊展開的那行，details 包住全部內容。

反思問題

  • 你的 PR 描述，審查者能在十秒內看懂這次改動的目的嗎？
  • agent 產出的文字裡，哪些是你真的看過、判斷過值得別人讀的？
  • 你的團隊有沒有約定，怎麼標示哪些內容是 AI 寫的、哪些是人確認過的？

延伸閱讀

  • datasette PR #3052：把單列頁面改成欄位清單的 PR，示範簡短開頭加截圖的寫法。
  • datasette PR #3042：改成按需載入編輯工具腳本的 PR，開頭一段說清楚問題與改法。
  • datasette-agent PR #51：新增 plugin hook 的 PR，文中用來示範 details/summary 的呈現。
  • llm PR #1838：新增管理 OpenAI 相容端點指令的 PR，開頭後附上指令說明輸出。

What Frontier Labs Buy: A Data Deep Dive with Handshake AI — Garrett Lord & Team

Handshake AI 現場示範前沿實驗室買的 RL 環境與評估長什麼樣子：模型常常懂規則，卻認不出規則該在哪一步套用，而只看最終回覆的評估會漏掉大部分問題。

重點

  • 金融環境裡，agent 要從銀行信箱找到任務、判斷哪些檔案適用，再交出試算表；它直接問能解釋稅務處理，實作時卻沒意識到該在哪一行套用。
  • 生物影像基準 VIALS 讓專家與模型比對腦腫瘤切片，模型多選了一張；看專家指出組織上缺了什麼，比看分數更有啟發。
  • 安全情境的評估會檢查 agent 讀了哪些檔案、有沒有核對副本、事後怎麼處理 shell 歷史，單看最後回覆會錯過大部分重點。
  • 節目也談到評分規則（rubric）跟專家判斷的落差、懲罰陷阱與部分給分的設計，以及 agent 曾經鑽 Excel 評分器漏洞的案例。

反思問題

  • 你評估 agent 時，看的是最終輸出，還是整段工具呼叫的過程？
  • 你的評分規則有沒有可能被 agent 鑽漏洞拿高分，卻沒真正完成任務？
  • 你的領域裡，有哪些專家判斷還沒被轉成可以自動檢查的評估？

延伸閱讀

  • ATLAS-Finance：讓 agent 在模擬銀行的信箱、文件與財務模型間工作的基準。
  • Evaluating AI agents inside a bank：追蹤另一筆公開案例從客戶信件到評分的完整過程。
  • VIALS：評估模型解讀科學家工作用影像的基準，含節目中的電泳膠與腦組織題目。

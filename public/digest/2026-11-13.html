Operate Claude Managed Agents inside your security perimeter

Claude Managed Agents 開放整套自架（私人測試版），而且不論誰託管，無人看管的 agent 安全都要靠架構先劃好界線，不能靠人逐步檢查。

重點

  • 自架版把 harness、沙箱、憑證與對話紀錄都放進自己的雲端或機房，模型請求可以直接送 Anthropic、雲端供應商或自家閘道，API 跟託管版一樣。
  • 「大腦」與「手」分開：agent 迴圈、紀錄與密鑰留在沙箱外，程式只在沙箱裡跑，沙箱需要時才啟動，掛掉也不影響整個任務。
  • 憑證不進沙箱：由沙箱外的代理程式在呼叫 MCP 工具或 API 時才補上憑證，自架時也能改用自己的密鑰管理服務。
  • 每個環境可以只允許特定主機連線，例如修 build 的 agent 只需要 git 主機和套件庫，其他一律擋掉。
  • 每一步工具呼叫與回傳都留下完整紀錄，並可透過 OpenTelemetry 匯出到既有的監控系統。

反思問題

  • 你的 agent 在沙箱裡跑時，碰得到哪些密鑰？真的需要碰到嗎？
  • 如果只能開放三個網域給 agent 連線，你會選哪三個？
  • agent 半夜自己跑完一個任務，隔天你能完整還原它做了什麼嗎？

延伸閱讀

  • Self-hosted Managed Agents 文件：自架整套服務的說明。
  • Self-hosted sandboxes：先前推出、只自架沙箱的做法。
  • Vaults：讓憑證留在沙箱外的機制。
  • Secure deployment：限制網路連線等安全部署設定。
  • Anthropic Engineering：Managed Agents：工程團隊對 Managed Agents 架構的說明。

The Jev Revolution: What Engineers Are Already Building with System One Models

System One 模型（只回傳選項、分數或機率的非生成式模型）又快又便宜又穩定，應該像函式一樣大量嵌進應用程式碼裡，而不是把所有判斷都丟給 LLM。

重點

  • TypeSafe AI 的 Almeida 認為 LLM 當軟體核心的問題在可靠度：大多時候很聰明、偶爾很離譜，又分不出哪次是哪種，就很難自動化。
  • 主張把決策模型的呼叫直接寫進程式碼，取代拼接字串再祈禱 LLM 回對的做法。
  • Glean 把 Jev 和 LLM、其他分類器混用，看中它不必重新微調就能應付分類項目變動；使用者不需要知道背後用的是哪種模型。
  • UiPath 用「淘汰賽」方式讓 Jev 分組挑出最相關的文件片段，上千次呼叫不到一秒；單次不聰明，靠組合策略變聰明。
  • Workday 的原型在使用者還在打字時就開始填請假卡，示範快速判斷能改變軟體本身的行為。

反思問題

  • 你的系統裡有哪些 LLM 呼叫，其實只是在做分類或打分？
  • 如果每次判斷只要幾十毫秒、幾乎不用錢，你會在哪些地方多加一次判斷？
  • 你怎麼知道模型這次的答案可不可信？有沒有信心分數可以用？

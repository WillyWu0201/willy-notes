AI Engineer Code Summit: OpenAI on New Ways of Working With Codex

OpenAI 在 AI Engineer Code Summit 的 Codex 工作坊重點：本機、雲端、個人代理和語音正在合成同一套工作方式，關鍵是別執著於目前的用法。

重點

  • Codex Cloud 改版後，可以把環境發布一次，再在隔離的副本裡平行跑多個任務，環境也能在公司內共用。
  • 本機與雲端的界線變模糊：可以直接請本機 Codex 把工作交給雲端接手，雲端只是另一個執行位置。
  • 語音不只是聽寫，講者把它當「控制台」，用來管理多條執行緒、查看進度、開新任務。
  • 個人代理 dots 的三種用法：當安全網提醒遺漏、當可以丟工作的地方，以及在各個工作場所都能找到它。
  • 收尾建議包括把 effort 調低、主動請 agent 幫忙，以及接受工具一直在變。

反思問題

  • 你的 agent 工作是綁在自己的筆電上，還是可以關機後繼續跑？
  • 有哪些「確認進度、開新任務」的瑣事，其實可以換個介面更快處理？
  • 你現在的 agent 用法裡，哪些是習慣而不是真的最有效？

Tests as data: ensuring AI-generated code does what we want

AI 同時寫程式和測試時，測試就不再可信。作者主張開發者要把自己當成客戶，用表格或 DSL 寫成資料檔的客戶測試當作人與 AI 之間的契約。

重點

  • 作者訪談的開發者普遍不信任測試，因為 AI 加功能時會連舊測試一起改，人不可能每次重讀。
  • AI 補的單元測試常大量用 mock，只證明 A 呼叫了 B，還會把現有 bug 當成正確行為鎖住。
  • 把測試縮成輸入、預期輸出與前置狀態，寫進 YAML 或 CSV，再請 AI 寫執行器，人一眼就看得出漏了哪些情況。
  • 測試放在資料檔，agent 偷改時差異很明顯；用有語法剖析的外部 DSL 強制每個案例都要有斷言，agent 較難寫出空殼測試。
  • 客戶測試不一定要走 UI，多數可以直接打服務層，跑得快也比較不會時好時壞。

反思問題

  • AI 上次改你的測試時，你能確定它沒有順便放寬判斷標準嗎？
  • 你的測試在證明「結果對不對」，還是只在證明「某個函式被呼叫了」？
  • 如果只能保留一份人看得懂的規格，你會選文字文件，還是一張可以執行的測試表格？

延伸閱讀

  • Approved Scenarios 與 Approved Logs（文中提到，未附連結）：Ivett Ördög 提出的模式，用 DSL 描述系統狀態、動作與結果，是 Constrained Tests 的一種。
  • Approval Tests（文中提到，未附連結）：Llewellyn Falco 推廣的做法，把系統輸出存成人可審核、可比對差異的文字檔。
  • Fit 與 specification by example（文中提到，未附連結）：用範例表格寫客戶看得懂的驗收測試，是本文做法的前身。
  • Go 的表格式測試（文中提到，未附連結）：Go 標準函式庫常用的寫法，例如 fmt 套件用一張案例表加一個小執行器測試。
  • Gherkin 與 Cucumber（文中提到，未附連結）：文中討論它們與 tests-as-data 的異同。

How Curative is building a national provider network with agents on Claude

保險公司 Curative 用一個主 agent 搭配審核、把關的小 agent 跑醫療院所簽約，關鍵不是給 agent 更多權限，而是用其他 agent 和人分層檢查，並從整批執行紀錄回頭改進系統。

重點

  • 工具越少越好：一開始做了多個專用工具效果不佳，最後只給一個「執行 Python」，合約修訂就交給模型自己用文件函式庫處理。
  • 權限分層放寬：超出標準費率先要人工核准，之後改由另一個較便宜的模型審核，大約三分之二能直接過，剩下的才交給執行長。
  • 每封對外訊息寄出前都有一個小模型把關，起因是主 agent 曾把內部底價筆記寄給對方；被擋下會附理由讓它重寫。
  • 每次執行只處理一家院所、不留跨案記憶；另一個有長期記憶的業務 agent 則可能記錯又清不掉，陷入惡性循環。
  • 改進在執行之外進行：定期讓 Claude Code 抽樣上萬筆紀錄、找出異常並直接開 PR 修正；也先在不碰個資的環境練習，再搬進受監管的資料。

反思問題

  • 你的 agent 拿到的工具是越多越好，還是一個夠通用的工具其實更可靠？
  • agent 出錯時，你是收回它的權限，還是加一層獨立的檢查者？
  • 你有沒有定期回頭看大量 agent 執行紀錄，從中找出要修的地方？

延伸閱讀

  • Claude Platform：Curative 建置這些 agent 所用的平台。
  • Python 的 docx 函式庫（文中提到，未附連結）：主 agent 用它在單一 Python 工具裡完成合約修訂與合併。

Designing for Agents — Zeno Rocha, Resend

開發者越來越常讓 agent 決定要用哪個服務，工具和文件要同時設計給人和 agent 用，被選中之後的實際交付品質才決定能不能留住使用者。

重點

  • agent 推薦工具時的第一順位影響很大：開發者接受 patch 之後，很少回頭試第二個選項，所以第一個被提出的服務占盡優勢。
  • 在 agent 出現之前先打進開發者的程式碼也有用：Resend 先推出能搭配其他寄信服務的 React Email，等開發者要換供應商時，它的程式碼已經在專案裡。
  • 給人的介面不一定適合 agent：價格頁的拖拉滑桿對 agent 不友善，網址加上 .md 就回傳一張表格，agent 一次請求就能讀完。
  • MCP 工具數量從二十個左右長到八十多個，目標是讓人在聊天介面也能做到後台能做的事；Cloudflare 則只開 search 與 execute 兩個工具，兩種設計可以對照。
  • 工具結果太大塞爆 context 時，減少工具數量並不能解決；實際展開每天用的工具回傳內容，看模型真正需要多少，是很便宜的檢查。

反思問題

  • 如果請 agent 幫你挑一個服務來實作某功能，它會選你的產品嗎？你知道它為什麼這樣選嗎？
  • 你的文件或價格資訊，agent 能不能用一次請求就讀懂？
  • 你最常呼叫的工具每次回傳多少資料？其中有多少是模型真正用得到的？

延伸閱讀

  • Claude Code 選用工具的研究報告：統計 Claude Code 在寄信服務上推薦誰當第一順位，並依模型與應用拆開比較。
  • React Email：Resend 早期推出的郵件範本工具，可以搭配其他寄信服務使用。
  • Cloudflare Code Mode MCP：只用 search 與 execute 兩個工具就開放整套 API 的 MCP 設計。
  • Resend MCP server：節目中討論工具數量時拿來對照的實例。
  • Anthropic：Writing tools for agents：工具回傳結果撐爆 context 時，如何讓回傳資料變少的具體做法。

Long-horizon agents and durable execution

要跑上好幾週的 agent，大部分時間都在等人和外部系統，途中當機、呼叫失敗、訊息重複都免不了；持久執行把每個對外步驟的結果記下來，重跑時跳過已完成的步驟並重建狀態，讓 agent 能接著往目標走。

重點

  • 長週期 agent 改變了成本算法：以前要人盯好幾週、回報不夠高就放著不做的事，例如帶新客戶上手、卡在部門之間的訂單、病患轉診與預約，現在變得划算。
  • 這裡的「長週期」指的是實際經過的時間，不是模型能連續工作多久。以補貨 agent 為例，詢價、等主管核准、下單、等貨到可能拖上數週，真正在運算的只有中間幾段。
  • 持久執行的核心：runtime 記錄每個與外界互動的步驟結果，程序掛掉後重新執行時，已完成的步驟直接跳過，狀態從紀錄還原；等待期間 workflow 暫停，不占運算資源。
  • 會改變外界的動作要經得起重做：範例下單時用採購單號當冪等鍵，確保供應商那邊只有一筆訂單，送出前也再核對一次價格是否仍在核准範圍內。
  • 作者也提醒持久不等於正確：agent 看不到的結果、等待期間外界已經變了、任務跑到一半程式碼改版、記憶該留什麼又該餵給模型什麼，都得另外設計。

反思問題

  • 你的 agent 如果跑到一半程序重啟，它知道哪些步驟做過、哪些還沒做嗎？
  • 你的工具呼叫裡，哪些重送一次就會造成重複下單或重複扣款？有沒有防護？
  • 你的流程中等人回覆的時間有多長？等待期間 agent 是不是一直占著資源？

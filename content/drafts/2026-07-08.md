## 接個視覺比對,還沒開始比就全紅

今天的主線是幫一套 UI 測試接上視覺回歸比對。需求很單純:給我 baseline 截圖,跑測試的時候順手截一張比對,不一樣的列出來、產一份報告。我本來以為難的是比對本身,結果卡我的是兩件設計階段根本沒放進腦子裡的事。

先講最蠢的那件。全螢幕像素比對,第一次跑,幾乎每張都紅。可是 UI 明明一個 pixel 都沒動。愣了一下,把 baseline 跟實際圖疊起來,差的是右上角——模擬器狀態列的時鐘,每分鐘跳一次;順帶訊號格、電量也會變。像素比對不管那是不是「內容」,它只知道這幾百個點跟上次不一樣。

解法是跑測試前把狀態列凍死:

```bash
xcrun simctl status_bar <udid> override \
  --time 09:41 --batteryLevel 100 --cellularBars 4
```

這種東西沒人會在畫設計的時候想到,但不先處理,整套視覺比對從第一天就是全紅——而且是那種你會信以為真、開始一張一張點開「到底哪裡變了」的全紅。最會騙人的失敗,是長得像真的失敗。

第二件是要拍板的:那個「截一張來比對」的動作,到底該插在哪。三個位置,各有各的毛病:

- **每個測案結束後自動截**(`afterTest`):最自動,測案一行都不用改。但測案「結束的那一刻」畫面常常不是重點——停在轉場動畫中間、鍵盤還開著、上一個 dialog 還沒收乾淨。這些全會變成誤報。
- **另外寫一支專門的視覺 spec**,自己導覽到各畫面逐一比對:報告乾淨、跟功能測試分離。但導覽路徑等於把現有 spec 再抄一遍,最不 DRY。
- **織進 page object 那些「已經到達某畫面」的 helper**——像 `reachHome`、`waitForForm` 這種節點:專案本來就有這些關卡,一次性在裡面各加一行比對,之後所有測案自動涵蓋,不用碰任何 spec。

我選第三個。但重點不是「哪個最自動」——真要比自動,`afterTest` 完勝,零成本。重點是這批截圖要能當報告交出去。`afterTest` 截的是「測案剛好停下的那一瞬間」,語意模糊又容易誤報;織進 helper 截的是「已經確定站在某個穩定畫面上」的那一刻——首頁就是首頁、表單就是表單,每次長得都一樣。報告上每一列都對得上一個真實畫面,而不是「某測案結束時剛好長這樣」。

最自動的那個做法,給你最沒用的報告。我寧可多花一次工,把比對織進那幾個 helper。

還有一條底線順手先劃好:視覺比對失敗,不能讓功能測案跟著 fail。它是加值資訊,不是新的驗收條件。所以那層包裝一定是 `try/catch` 全吞、永遠不 throw——比對不出來、截圖失敗、baseline 還沒建,通通只寫進報告,不去碰測案原本的綠燈。

## 一份給自己看的報告,還是被挑出 XSS


那份報告是我自己產的 HTML,產給我自己看的。review 的時候照樣被挑出一個洞:沒跳脫。

機制很單純:報告會把每一筆比對的畫面名稱、所屬測案標題、mismatch 百分比塞進一張 HTML 表格。測案標題是人手寫的字串——哪天有人在測案名字裡放個 `<img onerror=...>`,甚至只是單純打了一個 `<`,產出來的 HTML 就歪了,往壞裡說就是 XSS。

我第一反應是「這內部工具,誰會來攻擊自己的測試報告」。但這根本不是「誰會攻擊」的問題。是任何「把資料拼進 HTML」的地方,只要那份資料不是你當場寫死的字面值,就得跳脫。不然根本輪不到有人惡意——某個測案名字裡手滑多打一個角括號,報告自己就爛給你看。補上 escape、加個測試,收工。

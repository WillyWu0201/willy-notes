## 一排 skip,一半的理由是假的

今天花了大半天做一件聽起來很無聊的事:把一個跨平台 UI 測試套件裡那一長排 `it.skip` 掉的案子,一個一個撿回來。

先講背景。這套測試一路寫下來累積了不少 skip。有些是當初工具還驅動不了某個欄位,先跳過;有些是寫的人當下不確定那個行為到底算不算規格,不敢斷言,也跳過。跑起來報告都一樣:一排綠的 pass,加一句「N pending」。

問題就出在那句 pending。

它把兩種完全不同的東西混成同一坨。一種是「這個情境現在真的做不到」——這是工具的債,是外部限制。另一種是「我沒去確認這是不是對的行為」——這是人的債,是還沒做的功課。前者你短期無能為力;後者你其實今天下午就能去問到答案。但在報告上,它們長得一模一樣,都只是一個灰色的 skipped。

於是幾個月後回來看,你完全分不出哪排 skip 是「等工具」、哪排是「等某人去查一下」。整堆一起被當成「已知的、可接受的」放著。最貴的不是那些做不到的,是這些含糊的——因為它們佔著位子,看起來像是被交代過了。

今天拍的板是:skip 不能是免死金牌。要 skip 可以,但理由必須是**驗證過的**,不能是猜的。

分三種處置:

- 工具現在其實已經能驅動的 → 直接 un-skip,補回真正會斷言的測試。這批佔了最多。
- 真的被工具擋住的 → 留著 skip,但理由改成「已實測、確認是工具限制」,而不是含糊帶過。
- 講不清楚是不是規格的 → 這種最誠實的處理是去問;問到答案,它就變成前兩種之一。問不到、也證明現在無從驗證的,才留著,而且要寫明是「規格未確認」,不是「我覺得」。

示意一下差別(命名是示意):

```js
// 同樣是 skip,講的是三件不同的事
it.skip('送出後顯示正確的結果', () => { /* ... */ })
// ↑ 沒有理由。這種最糟,等於一張空白 IOU

it.skip('送出後顯示正確的結果 [tooling-blocked]', () => { /* ... */ })
// ↑ 已實測工具驅動不了,外部債,可接受

it.skip('送出後顯示正確的結果 [spec-unconfirmed]', () => { /* ... */ })
// ↑ 「我不確定規格」——十之八九是「我還沒去問」穿了件實驗衣
```

後來把這條規矩寫進團隊的 skill 文件,取名叫「the skip bar」:跳過一個測試是一個要過門檻的決定,不是預設選項。門檻就是——你得說得出一個別人可以驗證的理由。「我不確定」不算理由,它只是還沒查。

寫完才意識到,`spec-unconfirmed` 這個標籤我以前一直當成一個中性的、技術性的狀態在用。它不是。它多數時候就是「沒去確認」四個字,只是聽起來體面。把它改掉之後,那排 skip 一下少了三分之二。

## 一個沒清乾淨的衝突標記,溜進了 commit

另一件今天咬到我的,短很多,但很蠢。

type check 掛了。追下去,發現有個檔案裡躺著一組沒清掉的合併衝突標記——`<<<<<<<` 那一整套,直接被 commit 進去了。

會發生這種事,通常代表某次解衝突是用眼睛掃過、手一按就 commit,沒真的看內容。標記留在檔案裡,對 Git 來說完全合法,它不會攔你。真正攔下來的是編譯:那幾行不是合法語法,`tsc` 直接報錯。

有意思的是它並沒有讓任何測試變紅——因為跑那批測試的路徑根本沒把這個檔案編進去。換句話說,如果你的驗收只看「測試綠不綠」,這個壞掉的檔案可以一路綠燈開到底,是型別檢查那道跟測試分開的關卡才把它擋下來。

順手把標記清掉、連同一批冒出來的一個 Android 端型別錯誤一起修掉,`tsc` 就過了。

留一個心得給自己:type check 和 test run 是兩道不同的門,擋的東西不一樣。少跑其中一道,另一道的綠燈會給你一種它其實給不起的安全感。
